# Isolated browser runtime

## Status

The runtime is implemented under `backend/projects/browser_automation/`. It provisions fresh, run-scoped non-persistent contexts through the engine lifecycle adapter in `engines.py`. Playwright/Chromium remains the default and supports concurrent run contexts. Explicit user requests to open/show a browser launch a visible Chromium window; routine observation, research, and unattended checks stay headless, while explicit headless/background requests override. Visible contexts remain open after the task so the user can interact with the page, then are removed when the browser window closes; they still use an isolated context without the user's browser profile. Lightpanda 1.0.4 is an optional user-installed CDP backend for one active run context at a time; it returns PNG evidence, while Playwright returns JPEG, and cannot provide a visible desktop window. Its endpoint is restricted to loopback and must be started with private-network blocking. Both engines use the same request interception, host/IP validation, read-only request policy, action approvals, resource limits, and cleanup paths. The runtime supports bounded public-page navigation/observation plus state-bound actions, and closes contexts on explicit cleanup, run cancellation hook, or service shutdown. It also provides versioned local browser recipe storage and a deterministic internal executor with per-step checkpoints. The gateway adds durable per-step approval, event replay, screenshot artifacts, and a user-started recipe launch/results flow.

## User and service flow

Agent Chat exposes `browse_public_page` for a user-supplied public URL and `browser_action` for one state-bound action at a time. The tool verifies that the hostname appeared in the user task, asks the runtime for a run-scoped context, navigates, fetches the screenshot, saves it into the task output folder, and retains the context for further actions. User wording determines visibility from the original task: explicit open/show-browser intent opens visible Chromium, while passive page observation remains headless unless the user explicitly asks otherwise. Each observation has a new ID; actions with stale IDs are rejected. Click is limited to a named same-host link, typing to a named text/search field, selection to a named combobox, and scrolling to a fixed distance. In Default and Auto-review modes, every action except fixed scrolling pauses for approval. Full Access skips ordinary action approvals, while links whose accessible names suggest sending, submitting, purchasing, deleting, publishing, transferring, payment, or settings changes still require approval. Approval is bound to a hash of the exact validated action and current observation ID, expires after five minutes, and does not execute after rejection, expiry, or run cancellation. The approval card shows the action and target; typed values are never shown in the card or durable activity event. The gateway emits `browser_open`, `browser_action`, `browser_observation`, and `browser_screenshot` events; these are persisted with the other run events and replay in the chat timeline. Headless contexts close at task completion; visible windows remain open until the user closes them, and all contexts close on cancellation or service shutdown.

## API and data

See the route table and setup steps in [the browser automation project README](../../backend/projects/browser_automation/README.md). Browser contexts and runtime screenshot references are held in memory and keyed by a validated 32-character run ID. The agent tool copies screenshots into that run's local output folder for replay and download. No browser profile, cookie jar, credentials, or persistent browser directory is opened or written. Navigation accepts HTTP/HTTPS on standard ports, rejects URL credentials and non-public IPs, rechecks requests and redirects, and restricts a run to its initial hostname. Actions use accessible roles/names, require the latest observation ID, and return a fresh observation. Clicking is limited to same-host links; permission-mode approvals are described in the first section. Navigation and network-request counts, timeouts, and returned-text ceilings bound local operation. Health reports readiness, active contexts, and disabled profile persistence.

The browser service also owns the recipe persistence API. Definitions and immutable revisions are stored in `%LOCALAPPDATA%\FrogAI\browser-recipes.sqlite3` (or the path in `POCKPOCK_BROWSER_RECIPE_DB`), separate from run history and browser contexts. Schemas accept exact hostname allowlists, typed input declarations, named browser actions, required title/text stop conditions, and a fixed per-run approval policy. The first step must navigate to an allowed page. Type/select steps refer to declared inputs by name, so values are supplied at execution time and never saved into recipe files. Updates use an expected version to reject stale edits; disabling preserves history, while deleting removes the recipe and every version. The internal-token authenticated executor runs only the current enabled version in a fresh context, rejects invalid inputs, and stops on the first failed checkpoint. It returns ordered title/URL checkpoint results and always closes the context. The gateway local-only run route requests a fresh approval for every step and binds approval to the recipe/version/step/target/current observation plus a keyed fingerprint of transient input. Screenshots are copied into the task output folder before browser cleanup. Ordered approval, step, checkpoint, screenshot, and terminal events replay from the standard run history. The Browser recipes page provides explicit launch, transient inputs, live approval/progress, and screenshot results. It writes run events into the associated Conversations thread and lets the user reopen the latest recipe result after a reload. There is no schedule or background launch.

Health reports readiness, selected engine, active contexts, the engine context cap when limited, and disabled profile persistence.

## Permissions and failure behavior

The service binds to loopback. Context, navigation, action, evidence, close, and recipe-management routes require the shared service token. Chromium launch failure returns an unavailable response without exposing browser internals. Context close is idempotent. Downloads and service workers are disabled. There is no arbitrary script execution. Cross-host redirects and external subresources are blocked, so some pages may render without third-party assets. The model-callable tool rejects hosts absent from the original user request. Password fields, buttons, and form submission are blocked. A high-impact link is recognized from its accessible name; this heuristic cannot guarantee that an innocuous-looking link is harmless, so all non-scroll actions require approval in Default and Auto-review modes. Recipe storage accepts definitions only and does not store run-time input values.

Recipe execution events use the current durable run-event contract: `recipe_run_started`, `recipe_step_started`, `recipe_step_result`, and `recipe_run_finished`. Each event is bound to a recipe ID and immutable version; step events include a positive step number, and action-start events carry the current observation ID when one exists. Step results retain only the action name, checkpoint outcome, page title, URL, and retrieval time. Screenshots are saved as local task artifacts and referenced by a durable `browser_screenshot` event. Run-store validation rejects malformed fields and recursively rejects transient inputs, action values, credentials, passwords, authorization data, and cookies. Existing approval events remain separately persisted and carry the one-use approval ID/hash.

Compile with the project virtual environment, install Playwright plus Chromium as documented in the project README, start via the dashboard launcher, verify health and context lifecycle, then navigate to a public page and confirm the observation and screenshot can be retrieved. Also confirm loopback/private hosts and cross-host redirects are blocked.
